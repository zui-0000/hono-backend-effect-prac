# 05-01. このリポジトリの認証方式

方式そのものの解説は [`00-authentication-methods.md`](00-authentication-methods.md) にある。
ここは**このリポジトリが何を選び、何をまだ決めていないか**だけを書く。

> **状態**（2026-08-14）: login / refresh / logout の 3 本すべてが動作。
> Bearer の検証も入り、契約が `@useAuth` を宣言している 5 本が実際に閉じた。
> **未決だった Cookie への移行も完了**（[下記](#リフレッシュトークンは-httponly-cookie2026-08-14-に決定)）。
> 残るのは CORS だけで、それはフロントを繋ぐ移植先で入れる。

---

## 契約が既に決めていること

`schema/src/contexts/auth/` を読むと、**3 つの軸のうち 2 つは決着している**。

| 軸             | 答え                                | 契約のどこに書いてあるか                             |
| -------------- | ----------------------------------- | ---------------------------------------------------- |
| ① 状態を持つか | **券ごとに違う**（下記）            | `AccessToken` / `RefreshToken` の doc                |
| ② どう運ぶか   | **券ごとに違う**（下記）            | `LoginResponse` / `@cookie` / `@useAuth(BearerAuth)` |
| ③ 券は何枚か   | **2 枚（アクセス + リフレッシュ）** | `LoginResponse` + `Set-Cookie`                       |

### アクセストークンは JWT

```tsp
@doc("アクセストークン(JWT想定)。認可に使用する。")
// NOTE: JWT全体の厳密な検証は難しいため、3セグメント形式だけ軽く保証する
@pattern("^[A-Za-z0-9_-]+\\.[A-Za-z0-9_-]+\\.[A-Za-z0-9_-]+$")
```

**3 セグメント形式を pattern で強制している**ので、実装を JWT 以外にはできない。
つまりアクセストークンは**状態を持たない**（検証で DB を引かない）。

### リフレッシュトークンは不透明トークン

```tsp
@doc("リフレッシュトークン(不透明トークン想定)。アクセストークン再発行に使用する。")
// NOTE: 実装都合で形式を変えられるよう、JWTのような強い制約は付けない
```

形式を縛っていない＝**中身に意味を持たせない**。券だけ見ても誰のものか分からず、
サーバ側の記録を引いて初めて意味を持つ。

### そして失効させると宣言している

```tsp
/** ログアウト (要認証。リフレッシュトークンを失効させる) */
```

**「失効させる」と書いた時点で、リフレッシュトークンは保存が必要**になる。
JWT では失効させられないので、この 1 文が方式を決めている。

### 券の運び方は 2 つに分かれる（2026-08-14 に変更）

```tsp
model LoginResponse { accessToken: AccessToken; }        // 本文はアクセストークンだけ
op refresh(..., @cookie refreshToken: RefreshToken)      // 券は Cookie で受け取る
```

**アクセストークンは本文、リフレッシュトークンは HttpOnly Cookie。**
保護対象の操作は `@useAuth(BearerAuth)` なので `Authorization: Bearer <token>` で送る。

> かつては**両方をボディ**で受け渡していた（`LoginResponse` が 2 枚とも返し、
> `RefreshRequest` がボディで送り返す）。つまりクライアントの JS が
> 2 週間有効な券を保持する前提で、**XSS を踏んだ瞬間に盗まれる**形だった。
> 変更の経緯は[下記](#リフレッシュトークンは-httponly-cookie2026-08-14-に決定)。

## 採用する構成

契約から導くと、こうなる。

```text
アクセストークン    JWT・短命           → 署名検証だけ。DB を引かない
リフレッシュトークン ランダム文字列・長命 → DB に記録。失効できる。更新時に差し替える
運び方              アクセス: 本文 + Authorization ヘッダ
                    リフレッシュ: HttpOnly Cookie（JS からは読めない）
```

[`00-authentication-methods.md`](00-authentication-methods.md#構成の一覧) で言う
**「券を分ける（二段構え）」**にあたる。要件が正反対の 2 つを別の券に割り当てている。

|                    | 求めるもの                    | 割り当て |
| ------------------ | ----------------------------- | -------- |
| 毎リクエストの検証 | **速い**（DB を叩きたくない） | JWT      |
| ログアウト・失効   | **確実に止まる**              | DB 記録  |

毎回走る検証は回数が多いので DB フリーに、失効はログアウト時だけなので DB を叩いてよい。

### 受け入れている代償

**ログアウトは即座には効かない。** アクセストークンは DB を見ないので失効させようがなく、
最大でその寿命ぶん（15 分）は通り続ける（[理由](00-authentication-methods.md#代償ログアウトは即座には効かない)）。

即時性が要るなら寿命を短くするしかないが、そのぶん更新の頻度＝ DB アクセスが増える。
**このリポジトリでは「最大 15 分の遅延」を受け入れる。**
即時失効が要件になったら、そのときアクセストークン側にも失効リストを持つ話になる。

## 保存するもの

アクセストークン用のテーブルは**作らない**（状態を持たないため）。
リフレッシュトークンのぶんだけ要る。

```text
t_refresh_token                                  実装: contexts/auth/infrastructure/
  id          uuid         PK        券 1 枚の識別子（ローテーションのたびに変わる）
  session_id  uuid         INDEX     ログインからログアウトまで不変。JWT の sid はこれ
  token_hash  text         UNIQUE    券のハッシュ。券そのものは保存しない
  user_id     uuid         INDEX     誰のものか（**外部キー制約は張らない**）
  expires_at      timestamptz            長命側の期限
  revoked_at      timestamptz  NULL      失効した時刻
  revoked_reason  text         NULL      'rotated' | 'revoked'（後述）
  created_at      timestamptz
```

設計上の注意は 2 つとも [`00-authentication-methods.md`](00-authentication-methods.md#実装で踏みやすい落とし穴) に理由がある。

- **券の採番に `UuidGenerator` を使わない。** id は uuidv7 で統一しているが、
  券に必要なのは逆の性質（予測できないこと）。暗号論的乱数を使う。
- **券そのものではなくハッシュを保存する。** 高エントロピーな乱数なので
  argon2 は不要で、SHA-256 で足りる。

`revoked_at` を NULL 許容にして**行を消さない**のは、
「失効済みの券が使われた」を検出するため。それは盗難のサインなので、
検出したらそのセッションを切る防御につなげられる（範囲の決定は後述）。
下記のローテーションと組み合わせて初めて本領を発揮する
（消してしまうと、再利用が「知らない券」と区別できなくなる）。

`revoked_at` は**時刻**であって真偽値ではない。猶予期間の判定に「いつ失効したか」が要るため。

### 猶予期間は「失効の理由」で判定する

`revoked_at` だけでは足りない。**猶予期間はローテーション専用の救済**だから、
なぜ失効したかを記録しないと、ログアウトや盗難検出で切った券にも猶予が付く。

| 理由      | 意味                            | 猶予         |
| --------- | ------------------------------- | ------------ |
| `rotated` | ローテーションで置き換えられた  | **要る**     |
| `revoked` | ログアウト / 盗難検出で切られた | **要らない** |

これは机上の心配ではなく、**実際に踏んだ**。理由を持たず時刻だけで判定していたとき、
実 DB で次が起きた。

```text
1. 盗難を検出 → セッションの券をすべて失効させる   ✅ ここまでは正しい
2. その 30 秒以内に、失効した券のどれかを提示
3. 「失効済み・猶予期間内」と判定されローテーションが走る
4. 新しい券が発行され、**切ったはずのセッションが生き返る**
```

同じ理由で**ログアウトも 30 秒間は効かなかった**。契約は「ログアウトはリフレッシュ
トークンを失効させる」と言っているのに、その 30 秒だけ嘘になる。

修正は 3 箇所に及んだ。**1 箇所直しただけでは塞がらなかった**ので、順に残す。

1. `revoked_reason` 列を足し、`classifyRefreshToken` が理由を見るようにした。
   理由が読めない行（時刻はあるのに理由が無い）は `revoked` に倒す。
   迷ったら猶予を与えないほうが安全側に落ちる。
2. `revokeSession` を**セッションの全行**に当てるようにした。当初は
   「既に失効した行は触らない」と `revoked_at is null` で絞っていたが、それだと
   **ローテーション済みで猶予期間内の券が生き残る**。失効時刻のほうは `coalesce` で
   既存の値を残す（いつ最初に失効したかは監査の手掛かり）。
3. command の分岐を `if` の連なりから `switch` にした。
   `if (Reused) … / if (Expired) … / それ以外は差し替える` と書いていたため、
   新しく足した `Revoked` 状態が**黙って「差し替える」へ落ちていた**。

> **教訓が 2 つ。** ひとつは、状態が増える余地のある分岐を「それ以外」で閉じないこと。
> もうひとつは、**直したあとにもう一度測ること** — 1 の修正だけでは 2 の穴が残っており、
> 実 DB で確かめ直して初めて気付いた。
> この穴は**型・lint・テストがすべて緑のまま**存在していた。

### `session_id` を別に持つ理由

**券の id とセッションの id は別物**として持つ。JWT の `sid` に載せるのは `session_id` のほう。

券の id を載せると、**古いアクセストークンを持つタブからのログアウトが空振りする**。

```text
1. タブ A が更新   → row1 を失効、row2 を発行。タブ A は accessToken2 (sid=row2)
2. タブ B は accessToken1 (sid=row1) をまだ持っている（JWT なので寿命ぶん生きる）
3. タブ B でログアウト → row1 を失効させる（既に失効済み）
4. row2 は生きたまま。タブ A は更新し続けられる
```

しかも 204 が返るので**成功したように見える**。`session_id` をローテーションを跨いで
据え置けば、どのタブから叩いても同じセッションが落ちる。
「1 セッション = 1 デバイス」という直感とも一致する。

副産物として、[まだ決めていないこと](#まだ決めていないこと) にあった
「行の連鎖を持つか」が**不要になる**。`parent_id` で数珠つなぎにしなくても、
同じ `session_id` を引けば一族がまとめて取れる。

### 外部キー制約を張らない

`user_id` は `t_user.id` を指すが、**Drizzle でも DB でも FK は宣言しない**。

制約を張ると「**user コンテキストの削除が auth の都合で失敗する**」という結合が生まれる。
`deleteUser` の時点で券が残っていれば FK 違反で落ちる、という形で、
コンテキストを分けた意味が消える。参照整合性は DB 制約ではなく
**auth 側の手順**（user が消えたら券も片付ける）で保つ。将来 DB を分けても壊れない。

> `01-database.md` にはかつて「境界を跨ぐ FK も、相手コンテキストの `drizzle-schema.ts` を
> import すれば書ける」と書いていたが、それは `cross-context-public-only`
> （他コンテキストの非公開部分を禁じる）と**そもそも両立しない**。
> auth が初のコンテキスト跨ぎだったため、今日まで露見しなかった。記述は撤回した。

### テーブル名に所有コンテキストを含めない

`t_auth_refresh_token` ではなく `t_refresh_token`。`t_user_refresh_token` は
**所有者について嘘をつく**ので論外（置き場は `contexts/auth/` で、`user_id` は参照にすぎない）。

`t_auth_` 接頭辞の唯一の価値は「psql の中ではディレクトリ構造が見えない」への対処だが、
それが欲しいなら **Postgres のスキーマ**（`auth.t_refresh_token`）が本筋で、
接頭辞は名前空間を持てない環境での代用品。この DB は既に複数スキーマを使っている
（`drizzle.__drizzle_migrations`）ので、代用品を選ぶ理由が無い。

**見直す引き金**は、テーブルが増えて `\dt` が読みにくくなったとき
（目安: コンテキスト 3 つ・テーブル 10 枚）。そのときも接頭辞ではなくスキーマを検討する。

## 層の割り当て

`hono/jwt` に `sign` / `verify` / `decode` が入っており、**追加の依存は要らない**
（対応アルゴリズムは HS256/384/512、RS・PS・ES 各種、EdDSA）。

ただし **`hono/jwt` は実装**であり、`hono` は presentation の道具。
[`../02-architecture.md`](../02-architecture.md#ポートはそれを要求する層に置く) の規約どおり、
ポートと実装を分ける。

```text
shared/domain/access-token-issuer.ts              ポート（JWT の発行と検証）
shared/infrastructure/access-token-issuer-live.ts  実装（hono/jwt + Config で鍵を読む）

contexts/auth/domain/refresh-token-issuer.ts              ポート（券の生成とハッシュ化）
contexts/auth/infrastructure/refresh-token-issuer-live.ts  実装（Web Crypto + Bun.CryptoHasher）
```

`PasswordHasher` と `PasswordHasherLive`（`Bun.password`）の関係と同じ形。
**Bun を隠したのと同じ理由で Hono を隠す。** これを守らないと
`application-not-to-impl` が落ちるはずなので、ルールが先に教えてくれる。

**2 つの置き場が違うのは、要求する層が違うから。** アクセストークンの検証は
Bearer を見るミドルウェアが担い、それは全コンテキストのルートに掛かるので
auth の内側には置けない。リフレッシュトークンのほうは auth しか要求しない。
「ポートは、それを要求する層に置く」の素直な適用
（[`../02-architecture.md`](../02-architecture.md#ポートはそれを要求する層に置く)）。

鍵の検証は存在だけでなく**長さも見る**（32 文字以上）。未設定を弾くのは当然として、
短い鍵は総当たりで割られるうえ、割られても正常に動いて見えるため気付けない。

## user コンテキストとの境界

**初のコンテキスト跨ぎ**になる。ログインには
「メールアドレスで引く」「ハッシュを照合する」「id を券に載せる」の 3 つが要る。

`GetUserQueryService` は使えない。返すのは `name` / `mailAddress` だけで、
**`id` も `hashedPassword` も含まない**（`GET /users/{id}` のための射影として
意図的にそぎ落としてある）。

`UserRepository.findByMailAddress` は必要な情報を返す。**しかし使うべきではない。**
あれは書き込み側のポートで、`create` / `updateProfile` / `deleteById` まで
一緒に握ることになり、「書き込みは所有コンテキストの command を通す」が崩れる。

**user 側に auth 向けの読み取りポートを新設する**のが筋。
DDD の Customer/Supplier（使う側の要求を、供給側が受けて公開する）の初適用になる。

### 公開した面：`VerifyCredentialsQueryService`

```text
auth/application/login-command.ts
      ↓ これだけを使う（UserRepository には触れない）
user/application/verify-credentials-query-service.ts     ← 公開した面
      ↓ 実装は user の内側で
user/infrastructure/… → UserRepository + verifyUserPassword
```

```ts
execute: (params: { mailAddress: string; password: string }) =>
  Effect<Option<UserId>, RepositoryError>;
```

**ハッシュを返さず、照合ごと引き受ける形**にした。当初は `{ id, hashedPassword }` を
返して auth 側で照合する案だったが、そうすると得るものより失うものが多い。

- **同じ業務ルールを 2 か所に持つことになる。** 「このパスワードで合っているか」は
  既に user の domain にある（`verifyUserPassword`。ビジネス側に
  「パスワード変更のとき現在のパスワードを確認するか」を聞ける、という基準で内側に置いた）。
- **ハッシュが境界を越える。** 渡す情報は少ないほどよい。
- 副産物として、**auth は `PasswordHasher` を要求しなくなった**。
  auth が知るべきは「券をどう作るか」だけで、「パスワードをどう照合するか」ではない。

### 失敗は user 側で畳む

「利用者が居ない」と「パスワードが違う」を **どちらも `Option.none`** にまとめる。
書き分けると総当たりでメールアドレスの登録有無を判定できてしまう（アカウント列挙）。
401 へ翻訳するのは auth の責務。**実測で応答本文が 1 バイトも違わないことを確認済み。**

### 入力は素の string、返す id は branded

非対称に見えるが、**使われ方で決めている**。入力は「照合してもらう材料」で、
値オブジェクトへの変換は所有者である user の仕事。一方 id は auth 側で
`RefreshToken` 集約の項目になる（あちらの `userId` は `UserId` 型）ので、
素の string で返すと**自分の DB から出したばかりの値を境界の向こうで検証し直す**
という無駄が生まれる。

`GetUserQueryOutput` が素の string なのは、あれが HTTP 応答へ直行して
ドメインの値として使われないため。**射影だから常に素、ではない。**

### Query なのに domain を経由する

`get-user-query-service.ts` には「Query は domain を経由しない」と書いてあり、
`VerifyCredentialsQueryServiceLive` は**その例外**にあたる。
照合が業務ルールとして既に domain にあるためで、経由を避けて `PasswordHasher` を
直接叩くと上記のとおりルールが 2 か所になる。
**射影を返すという性質より、ルールを 1 つに保つほうを採った。**

### ルールが止めるようにした（2026-08-12）

かつてここには「**ルールは止めてくれない**」と書いてあった。当時の
`no-cross-context-internals` が禁じるのは相手の `infrastructure` / `presentation` だけで、
`UserRepository` は `domain/` にあるため **auth から import しても lint が通った**。
守っているのは規約と人間の判断だけ、という状態だった。

`cross-context-public-only` へ改め、**allowlist に反転**した。他コンテキストから
見えるのは `<ctx>/public/` と `<ctx>/domain/model/value-objects/` の 2 つだけで、
`UserRepository` も `User` 集約も `application/` も届かない。
`VerifyCredentialsQueryService` が `public/` に居るのはこのため。

値オブジェクトを通すのは、**振る舞いもライフサイクルも持たない**から。
渡しても書き込み権限が付いてこないし、業務ルールが変わっても形が変わらない。
`RefreshToken` が `userId: UserId` を持つのがこの経路（集約は ID で参照する）。

## ローテーションを入れる（決定）

更新のたびにリフレッシュトークンごと差し替え、古いほうを失効させる。
**ただし猶予期間とセットで。**

採る理由は、この構成では**リフレッシュトークンをクライアントの JS が保持する**から。
契約がボディで受け渡す形なので置き場が盗まれやすく、
「盗まれたと気付ける」価値が相対的に高い（[仕組み](00-authentication-methods.md#ローテーション--リフレッシュトークンも入れ替えるか)）。

猶予期間を必ず併せるのは、**並行リクエスト問題**で正規の利用者を締め出さないため。
アクセストークンが切れた瞬間に画面が複数の API を同時に投げると、
先頭以外が「失効済みの券」を提示することになり、**盗難と誤検出される**。

| 対策                                      | どこで       |
| ----------------------------------------- | ------------ |
| 更新を 1 本に絞る（更新中は他を待たせる） | クライアント |
| **差し替え後 N 秒は古い券も受け付ける**   | サーバ       |

> 守るための仕組みが守るべき相手を締め出す——**セキュリティ機能の失敗はだいたいこの形**。
> ローテーションだけ入れて猶予期間を忘れる、というのが典型例。

### 契約の変更（2026-08-08 に適用済み）

`RefreshResponse` はアクセストークンしか返していなかったので、差し替える券を足した。

```tsp
model RefreshResponse {
  accessToken: AccessToken;
  refreshToken: RefreshToken;   // ← 追加
}
```

**項目の追加なのでクライアントは壊れない**（既存の実装は知らない項目を無視する）。
[`../../CLAUDE.md`](../../CLAUDE.md) の基準では破壊的変更にあたらないため `!` は付けない。

## Bearer の検証は routes の宣言に混ぜる

認証を Hono のミドルウェア（`app.use("/users/*", …)`）にはしていない。
`handleWithEffect` の **第 5 の入力源**として宣言する。

```ts
handleWithEffect({
  request: { header: GetUserHeader, params: GetUserParams, auth: true },
  response: { status: HttpStatus.Ok, body: GetUser200Response },
  controller: getUserController,
})(runtime);
```

理由は 3 つ。

- **契約と 1 対 1 になる。** TypeSpec の `@useAuth(BearerAuth)` が付いている
  エンドポイントに `auth: true` を書く。routes を見れば認証の要否が
  他の宣言と同じ場所で読める。パスのパターンで別に管理すると**二重管理になり、
  付け忘れても何も起きない**。
- **宣言し忘れが型に出る。** 宣言していない controller が `auth` を触ると
  コンパイルエラーになる（`header` / `body` / `params` / `query` と同じ扱い）。
- **controller への受け渡しが型付きになる。** ミドルウェアだと `c.get("claims")` の
  ような弱い経路が要る。

副次的に、**認証を要求するエンドポイントを持つコンテキストの Runtime に
`AccessTokenIssuer` が現れる**。要求が型に出るので、結線し忘れは起動前に分かる。

失敗はすべて `UnauthorizedError` に丸める。ヘッダが無い・形式が違う・署名が不正・
期限切れを書き分けない。

検証は**入力の検証より先**に走らせる。**認証を通っていない相手には契約の話を
一切しない**ため。後にすると 400 の `details` がフィールド名と制約をそのまま返し
（`password は 12 文字以上` など）、要認証の経路でもそれを誰にでも渡すことになる。

> 当初は逆で、「契約違反 400 が先に分かるほうが直しやすい」を理由に最後へ置いていた。
> **2026-08-09 に前へ移した。** 旧案で得をするのはトークンもボディも両方壊れている
> ときだけで、それは認証を直せば済む。守るものの大きさが釣り合っていなかった。

### 契約の嘘を回収した

`@useAuth(BearerAuth)` は 5 本に宣言されていたが、**実装は誰でも通していた**。
承知のうえで先送りしていた状態で、コード側にも
「認証は auth コンテキストの実装後に追加する」と書いてあった。

`auth: true` を付けた時点で **HTTP 境界のテストが 11 本落ちた**。落ちたこと自体が
「これまで認証なしで通っていた」証拠になる。テストには Bearer を送るよう直したうえで、
**認証が効いていること自体を固定するケースを別に足した**（ヘッダ無しで 401、
作成だけは 201、署名検証に失敗すれば 401）。
これが無いと、次に壊れたとき 200 系が返るだけで気付けない。

## クライアントに求めること

フロントエンドは別リポジトリになるが、**サーバの設計はクライアントの振る舞いを前提にしている**。
とくに猶予期間は「クライアントが並行して更新を投げる」ことを織り込んだ仕組みなので、
何を期待しているかをここに書いておく。

### 更新は 2 段構えにする

```text
土台（正しさ）:  リアクティブ  — 401 が返ったら更新し、元のリクエストを再送する
上乗せ（快適さ）: プロアクティブ — 期限の少し手前で先回りして更新する
```

**タイマーは最適化であって、正しさの土台にはできない。**

| 場面               | タイマーに起きること                                       |
| ------------------ | ---------------------------------------------------------- |
| タブが非アクティブ | ブラウザが `setTimeout` を間引き、**発火が遅れて期限切れ** |
| PC がスリープ      | 寝ている間は進まない。復帰時にはとうに切れている           |
| リロード           | タイマーごと消える                                         |

「切れていたら直す」を土台に置けば、タイマーが裏切っても最終的に必ず復帰する。
逆にリアクティブだけだと**期限切れ直後の 1 リクエストが必ず往復 2 回**になるので、
その体感を消すのがプロアクティブの役目。**役割が違う。**

### 実装で押さえること

1. **タイマーの時刻は JWT から読む。**
   アクセストークンの寿命を別途覚えておく必要はない。
   [JWT は署名されているだけで暗号化されていない](00-authentication-methods.md#3-jwt-は暗号化されていない)ため、
   クライアントが `payload.exp` を読める。**リロード後も手元の券からタイマーを復元できる。**
2. **`exp` ちょうどではなく手前に張る。**
   クライアントとサーバの時計はずれる。30 秒程度の余裕を持たせないと、
   **切れた後に更新へ行く**ことになる。
3. **更新は 1 本にまとめる。**
   更新中のプロミスを 1 つ保持し、更新が必要な呼び出しは全部それを待つ。
   3 本同時に 401 が返っても、実際に飛ぶ更新リクエストは 1 本になる。

### タブを跨ぐぶんはサーバが引き受ける

上記 3 が効くのは**同一タブの中だけ**。タブが 3 枚開いていればタイマーも 3 つあり、
それぞれが更新を投げる。クライアント側のミューテックスでは止められない。

**ここを拾うのがサーバ側の猶予期間**（[ローテーションを入れる](#ローテーションを入れる決定)）。
クライアントに完璧な協調を要求せず、**サーバ側で誤検出を吸収する**という分担にしている。

## 決めた値（2026-08-08）

実装に入る前に、未決だったものを確定させた。

| 論点                 | 決定                                                   |
| -------------------- | ------------------------------------------------------ |
| アクセストークン     | **15 分**                                              |
| リフレッシュトークン | **2 週間**                                             |
| 猶予期間             | **30 秒**                                              |
| 猶予期間中の応答     | **通常どおりローテーションする**（新しい券を発行する） |
| 署名アルゴリズム     | **HS256**                                              |
| 盗難検出時に切る範囲 | **そのセッションだけ**（全セッションではない）         |

**猶予期間は幅の上限（30 秒）を採った。** 短くするほど、タブ跨ぎの並行更新で
正規利用者を締め出す確率が上がる。盗難側のリスクは「30 秒だけ古い券も通る」程度で、
[締め出しのほうが実害が大きい](00-authentication-methods.md#ただしそのままでは正規利用者を締め出す)。

**猶予期間中も新しい券を発行する。** 一度は「同じ券をそのまま返す」と決めたが、
**実装できないので撤回した**。券は平文で保存していないので、
「さきほど別のタブへ渡した券」の平文はサーバのどこにも残っていない。
返しようがない。

| 案                                   | 可否                                                                   |
| ------------------------------------ | ---------------------------------------------------------------------- |
| 提示された古い券をそのまま返す       | **危険**。失効済みなので、猶予期間が切れた次の更新で盗難と誤検出される |
| 新しい券の平文を猶予期間だけ保存する | **論外**。ハッシュ保存の意味が消える（DB が漏れれば生きた券が漏れる）  |
| **猶予期間中も通常どおり発行する**   | 採用                                                                   |

「30 秒は古い券も受け付ける」という**目的は変わらない**。変わるのは応答の中身だけで、
並行して更新を投げたタブはそれぞれ自分の券を受け取って動き続ける。

行が増えるのは受け入れる。タブごとに券を持つならどれも使われるし、`localStorage` で
共有していて孤児が出ても、`expires_at` で自然に死に、ログアウトすれば `session_id` で
まとめて失効する。**盗難検出も壊れない** — 攻撃者が使えばその券は失効して次に移り、
正規利用者が同じ券を使ったときに「失効済み・猶予外」として検出される。

> **なぜ間違えたか。** 応答の形を、保存方式を確かめずに決めた。
> 「ハッシュしか保存しない」は同じ doc の数十行上に自分で書いてあったのに、
> 猶予期間の議論のときに結び付けられなかった。
> **決定どうしが矛盾しないかは、実装に落とす前に一度突き合わせること。**

**署名は HS256。** 非対称（RS256 等）が要るのは発行と検証が別サーバのとき。
このリポジトリは同一プロセスで完結する。

**盗難検出時はセッション単位で切る。** 失効済みの券が猶予期間の外で使われたら
盗難のサインだが、**猶予期間を入れてもなお誤検出は起こりうる**（時計のズレ、
極端に遅いネットワーク、リトライの重なり）。全セッションを切ると、誤検出のときに
正規利用者が全端末から締め出される。まず狭く切り、必要になったら広げる。

## リフレッシュトークンは HttpOnly Cookie（2026-08-14 に決定）

長らく「まだ決めていないこと」の唯一の項目だった。**引き金は「フロントの構成が
決まったとき」**と書いてあり、それが引かれた——別リポジトリ
（`aws-infra-practice` の `full-stack-ts-aws-ecs`）で React SPA +
サブドメイン分離の構成が固まったため。判断の全文は向こうの
`docs/初期構想/02-認証方式.md` にある。ここには**この repo に入れた結果**を書く。

### 判断軸は SSR ではなく XSS だった

ここには「SSR を前に置くなら Cookie が要る」と書いてあった。その軸だと
React SPA なら「Bearer のままでよい」になる。**その軸が不十分だった。**

```text
旧: refreshToken (2 週間) をクライアントの JS が保持する
    → XSS を踏んだ瞬間、2 週間有効な券が盗まれる
```

この doc 自身が「契約がボディで受け渡す形なので**置き場が盗まれやすく**、
『盗まれたと気付ける』価値が相対的に高い」と書いてローテーションを採用していた。
**その前提条件のほうを潰した**、というのが今回の変更。

### 採った形

```text
アクセストークン (15 分)      → 本文。JS のメモリに置く（localStorage には置かない）
リフレッシュトークン (2 週間) → HttpOnly Cookie
    HttpOnly; Secure; SameSite=Lax; Path=/auth/refresh; Max-Age=1209600
```

`Path=/auth/refresh` に絞るのが要点。**更新以外のエンドポイントには一切飛ばない**ので
漏洩面が最小になる。

**得るものだけではない。心配ごとが 1 つ消えて 1 つ増える。**

|                  | 得る                                 | 失う                            |
| ---------------- | ------------------------------------ | ------------------------------- |
| Bearer 一本      | CSRF を考えなくてよい                | XSS で 2 週間の券が盗まれる     |
| **ハイブリッド** | XSS で盗まれるのは最大 15 分の券だけ | **CSRF という考慮事項が増える** |

`SameSite=Lax` と CORS の Origin 制限でほぼ塞がる。**「XSS のほうが CSRF より怖い」
という重み付けを採った**、というのが判断の実体。

### 契約の変更（破壊的）

```text
LoginResponse    refreshToken を外す（accessToken だけ）
RefreshResponse  refreshToken を外す（accessToken だけ）
RefreshRequest   モデルごと削除（ボディが空になる）
refresh          @cookie refreshToken: RefreshToken を受ける
login/refresh    Set-Cookie を返す（AuthResponses.tsp）
logout           Set-Cookie で消す（同上）
```

`schema/` が変わりクライアントが壊れるので、
[`../../CLAUDE.md`](../../CLAUDE.md) の基準どおり `!` が付く。

### `@useAuth` ではなく `@cookie` にした

向こうの doc は `@useAuth(ApiKeyAuth<ApiKeyLocation.cookie, "refresh_token">)` を
指定していたが、**`@cookie` に変えた**。理由は向こうの doc が挙げた目的
（契約に現れないと二重管理になる）に、こちらのほうが近いから。

|                             | OpenAPI に出るもの                               |
| --------------------------- | ------------------------------------------------ |
| `@useAuth(ApiKeyAuth<...>)` | securityScheme。「資格情報がある」としか言えない |
| **`@cookie`**               | **`in: cookie` のパラメータ。値の型まで出る**    |

> **ただし二重管理は消えなかった。** orval は Cookie パラメータのスキーマを
> **生成しない**（ヘッダとパスパラメータは生成するのに、Cookie だけ落ちる。実測済み）。
> そのため検証スキーマは
> [`refresh-cookie.ts`](../../src/contexts/auth/presentation/refresh-cookie.ts) に
> 手書きが残り、長さの制約（20〜2048）を契約と二重に持っている。
> **消せる引き金は orval が Cookie パラメータを生成するようになること。**

### 応答側は `@cookie` が使えない

`@typespec/http` 1.14.0 は**応答の `@cookie` に未対応**。書くと
`response-cookie-not-supported` の警告が出たうえ、**そのプロパティは黙って本文から落ちる**。
コンパイラ自身が「`Set-Cookie` が要るなら `@header` を使え」と案内するので、
応答側は `@header("Set-Cookie")` で宣言している。**入口と出口で書き方が非対称**になる。

### 実装に入れたもの

`handleWithEffect` の設計がそのまま効いた。**入力源を 1 つ足すだけ**で済んでいる。

```text
validateJson / validateHeader / validateParams / validateQuery
  + validateCookie      ← 追加（getCookie(c) を decodeInput に通すだけ）
```

出力側は**ステータス × 本文の有無**の 2 軸に、**Cookie という 3 つ目の軸**が増えた。
Cookie はステータスと直交する（ログインは 200 + Cookie、ユーザー取得は 200 のみ、
ログアウトは 204 + Cookie）ため、任意フィールドとして足してある。
**「204 に本文」が書けない**という元の性質は保たれている。

属性を書いてよいのは
[`refresh-cookie.ts`](../../src/contexts/auth/presentation/refresh-cookie.ts) の 1 箇所だけ。
発行と削除が**同じ関数を通る**ので、`Path` や `Domain` がズレようがない
（1 つでも違うとブラウザは別の Cookie とみなし、**消したつもりで残る**）。

環境で変わる `Secure` と `Domain` だけ `CookieSettings`（`shared/domain/` のポート）から
読む。**既定は `Secure` を付ける**——設定を忘れた環境が安全側に倒れるように。

### ログアウトは Cookie も消す

向こうの doc に無かった点。**サーバ側でセッションを失効させるだけでは足りない。**
消さなければブラウザは 2 週間送り続ける。実害は「必ず 401 になる券が飛ぶ」程度だが、
失効済みの券が届き続けると**盗難検出のログがノイズで埋まる**
（`revoked_reason = revoked` の券は再利用検出の対象でもある）。

### 残っていること

**CORS はこの repo に入れていない。** フロントが無いので検証する相手がおらず、
向こうの doc 自身が「CORS と Cookie の実地検証は `dev1` が初出」と認めている。
移植先で `origin` と `credentials: true` を入れる（`credentials: true` と
`Access-Control-Allow-Origin: *` は**仕様上併用できない**）。

## 着手前に片付けること（2026-08-08 に完了）

「`process.env.DATABASE_URL!` の起動時検証」を先送りから昇格させる、と書いていた。
**着手前に片付けた**（[`../04-backlog.md`](../04-backlog.md#processenvdatabase_url-の起動時検証2026-08-08-に解決)）。

当時はこう書いていたが、**前半は誤りだった**。

```text
DB の接続文字列が未設定 → 最初のクエリで失敗する。すぐ気付く   ← 誤り
署名鍵が未設定         → 空の鍵で署名し続ける。エラーは出ない
```

実測したところ、`Bun.sql` は未設定をエラーにせず**既定の接続先へフォールバックする**。
localhost に OS ユーザー名で繋ぎにいくため、設定漏れは「動かない」ではなく
「**別の DB に繋がる**」に化ける。つまり DB 接続文字列も、質としては署名鍵と同類だった。

いまはアプリ側が Effect の `Config`、道具側（`db/migrate.ts` / `drizzle.config.ts`）が
`db/database-url.ts` で、どちらも起動時に落ちる。**`JWT_SECRET` も同じ経路に乗せる** —
`TokenIssuerLive` で `Config.redacted("JWT_SECRET")` を読めば、
`DatabaseLive` と同じく Layer の構築時点で落ちる。

署名鍵が未設定のまま動くと、**誰でも偽造できるトークンを発行しながら正常に見える**。
起動しないほうが圧倒的にましなので、ここは defect（`Layer.orDie`）で構わない。
