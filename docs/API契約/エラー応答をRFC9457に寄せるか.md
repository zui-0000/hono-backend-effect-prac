# エラー応答を RFC 9457（Problem Details）に寄せるか

**結論: 寄せない。語彙の借用もしない（2026-08-14）。**
`{ errorCode, message, details }` を据え置く。

---

## 何に迷ったか

[`04-backlog.md`](../04-backlog.md) の「契約を 2026 年時点の一次情報で洗い直す」が、
エラー応答を唯一の**ズレ**として挙げていた。

```text
記事の推奨   Problem Details（RFC 9457）
この repo    独自 { errorCode, message }        ← ズレ
```

RFC 9457 は `application/problem+json` という専用の media type と、
`type` / `title` / `status` / `detail` / `instance` の 5 メンバ（**全て任意**）を定める。
拡張メンバも明示的に許可されている。

## メンバごとに採点した

| メンバ                     | この repo にとって                                             | 判定 |
| -------------------------- | -------------------------------------------------------------- | :--: |
| `type`                     | `errorCode` と役割が完全に重複                                 |  ✗   |
| `title`                    | 今の `message` の改名。得るものが無い                          |  ✗   |
| `status`                   | HTTP ステータス行の写し                                        |  ✗   |
| `detail`                   | **設計と正面から衝突する**（下記）                             |  ✗✗  |
| `instance`                 | 相関 ID を本文にも載せられる。ただし `X-Request-Id` に既にある |  △   |
| `application/problem+json` | 汎用クライアントが認識できる。**その汎用クライアントが居ない** |  △   |

## 決め手

### ① `detail` は「原因を外に出さない」方針と衝突する

RFC の `detail` は「**この発生に固有**の説明」。この repo は意図的に逆をやっている。

- `UnauthorizedError` は `message` を持たない（どこで失敗したかを書き分けない）
- `error-message.ts` の doc —「内部で何が起きたかは `logFailure` がサーバーログに残すので、
  ここは外部に見せてよい定型文だけにする」

RFC の推奨に従うと、**わざわざ塞いだ情報漏れの経路を開け直す**ことになる。

### ② 価値が出るのは外部の消費者が居るときだけ

実利があるのは `instance`（相関 ID）と media type の 2 つだが、どちらも
**API を知らない相手**——API ゲートウェイ、監視ツール、Problem Details 対応の
クライアントライブラリ——に向けたもの。いまは 1 つも居ない。
払うのは確実で、得るのは仮定の未来。

### ③ 「語彙だけ借りる」案も検討し、これも落とした

`errorCode` → `type`、`message` → `title` と改名し、media type は
`application/json` のままにする案（`{ status, type: "4000", title, details }`）。
実際に一度この形で合意しかけたが、**改名部分の得がすべてゼロ**だった。

決定的なのは `type` という名前が成り立つ理由。RFC が `type` の一語で済ませられるのは、
**media type が「この本文は problem である」と先に宣言している**から。
`application/json` で返すとその文脈が消え、残るのは
プログラミングで最も使い回される単語が値 `"4000"` を持つだけの、曖昧なフィールドになる。

`errorCode` は前に立つ `error` が「何の」を説明しているので、単体で読める。
**改名は名前を悪くする変更だった。**

> **`type: "4000"` は準拠を名乗った瞬間に壊れることも確認した。**
> RFC の `type` は URI 参照で、クライアントは基底 URI に対して解決する。
> `"4000"` は相対参照なので、`GET /users/123/sessions/456` が返す 400 では
> `…/users/123/sessions/4000` に解決され、**同じ事由が経路ごとに違う識別子になる**。
> 準拠するなら `urn:problem:4091` のような絶対 URI か、
> 少なくとも `/problems/4091` とルートを付ける必要がある。

## 副産物 — 本物の問題が 1 つ見つかった

RFC とは無関係に効く。`errorCode` は `<HTTP ステータス><連番>` の 4 桁なので、
**識別子の中に HTTP ステータスが埋まっている**。

ステータスを変える判断をすると、規則に忠実な限りコードも動く。
だが事由は何も変わっていないのに、クライアントの分岐は壊れる。
実際 `ForbiddenError` は 404 に畳む形で一度実装し、その後 403 へ戻している。

**先頭 3 桁は「作られたときのステータス」と定義し、以後は動かさない**ことにした
（`src/shared/presentation/constants/error-code.ts` に明記）。
裏を返すと先頭 3 桁は将来ズレうるので、**読み替えの根拠は HTTP のステータス行**とする。

## 引き金

- **外部の消費者が現れたとき。** 他社が叩く API になる、API ゲートウェイを挟む、
  監視ツールにエラーを分類させる、のいずれか。そのとき `type` を URI にする話と
  セットで再検討する。
- ただし `detail` は引き金が引かれても採らない見込み。あれは方針の衝突であって、
  外部消費者の有無とは無関係。

## 決めておくこと

**この形は RFC 9457 ではない。** 似た項目（`details`）を持つが、
語彙も media type も借りていない。Problem Details 対応のライブラリに食わせないこと。
