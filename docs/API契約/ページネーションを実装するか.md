# ページネーションを実装するか

**結論: 実装しない。用意してあった型も消した（2026-08-14）。**

---

## 何に迷ったか

[`04-backlog.md`](../04-backlog.md) はこれを **⑦ の最優先**と位置づけていた。

> `schema/src/shared/pagination/` に用意してある `CurrentPage` / `PerPage` / `TotalPages` は
> **ページ番号方式**で、デファクト（GitHub / Stripe のカーソル方式）と別物。
> `listUsers` はまだ契約が未定義なので、**書き始める前なら型を捨てるだけで済む**。

「期限がある判断」として扱っていた。契約を書いた瞬間に方式が固定されるため。

## 前提が消えた

**`listUsers` を実装しないと決めた。** そうすると「カーソル方式かページ番号方式か」は
**実装する側の判断**なので、決めても使われない。期限も存在しない。

## 型を消した理由

**未使用の型は「これから使う」と読める。** 残すと嘘をつく。

消す前に測った。

```text
CurrentPage / PerPage / TotalCount / TotalPages
  定義元以外からの参照        0 件
  schema/dist/openapi.yaml    0 件（TypeSpec が未使用モデルを落とす）
  削除後の openapi.yaml       差分なし（バイト単位で不変）
```

`schema/src/shared/index.tsp` のバレルが import していたので**コンパイルは通るのに、
成果物には 1 行も出ない**状態だった。消しても失うものが無いことは出力の差分で確認済み。

判断の経緯は文章として残るので、型のファイルを記念に取っておく理由はない
（`db-only-from-infrastructure` を冗長になった時点で消したのと同じ扱い）。

## 復活させるときに見ること

1. **方式をゼロから決め直す。** 消した型はページ番号方式なので、そのまま作り直さない。
   デファクトはカーソル方式（GitHub / Stripe）。
   出典は [Web API 設計の現在地 2026](https://qiita.com/tatsuya582/items/a800739c02eadff68c70)。
2. **標準が無い領域**であることを踏まえる。RFC で決まっているものではないので、
   「デファクトに合わせる」を採るかどうかがそのまま判断になる。

## `validateQuery` は残す（意図的）

クエリパラメータを使うエンドポイントは 1 本も無く、
[`validate-request.ts`](../../src/shared/presentation/handler/validate-request.ts) の
`validateQuery` は**一度も実行されない**。それでも消さない。

**この repo のバックエンドは汎用の土台として作っているため。** `request` の入力源を
header / body / params / query の 4 つ揃えてあること自体が設計で、
「いま使う経路が無い」は消す理由にならない。

引き換えに**永久に未検証**の経路が 1 つ残る。実行されないので API テストでは覆えず、
埋めるなら単体テストになる（[`04-backlog.md`](../04-backlog.md) の
「単体テストの追加」で扱う）。
