# 用語集

境界の話で出てくる語。**この repo の実物と対応づけて**書く。

---

## 先に: 「上流/下流」は、レイヤーの上下と方向が逆

**いちばん混乱するのがここ。** 用語が 2 系統あって、指す向きが反対になる。

| 言い方              | 何を基準にしているか             | `auth` はどっち |
| ------------------- | -------------------------------- | --------------- |
| **レイヤーの上下**  | **呼ぶ側が上**（呼び出しの方向） | **上位層**      |
| **DDD の上流/下流** | **影響が流れる向き**（川の比喩） | **下流**        |

**`auth` は「上位層」であり、同時に「下流」。** どちらも正しい。

DDD の方は**川の比喩**で考える。

```text
user（上流）が形を変えたら、auth（下流）が壊れる
auth（下流）が何をしても、user（上流）は壊れない
```

> **Customer-Supplier パターンでは、Supplier が上流、Customer が下流。**
> 上流のコンテキストは下流に影響を与えるが、その逆は成り立たない。
> — [Open Group: DDD Strategic Patterns](https://pubs.opengroup.org/architecture/o-aa-standard/DDD-strategic-patterns.html)

つまり **「呼ぶ / 呼ばれる」ではなく「壊れる側がどっちか」**で決まる。
`VerifyCredentialsQueryService` の形を user が変えれば auth が壊れ、逆は起きない。
だから user が上流。

そしてこれが [ACL](#腐敗防止層anti-corruption-layer-acl) の置き場も決めている。
**被害を受ける側が防具を着る**ので、ACL は下流に置く（川下の人が浄水器を置く）。

## 顧客/供給者（Customer/Supplier）

上流と下流のチームがあり、**下流（使う側）の要求を上流（供給側）が受けて公開する**関係。
上流には下流の都合に応える義務がある、というのが他パターンとの違い。

**この repo**: auth（Customer）が「照合してほしい」と要求し、
user（Supplier）が `VerifyCredentialsQueryService` を公開した。

だから公開の向きは常にこう。**要求が先、公開が後。**

```text
auth「メールとパスワードで本人か確かめたい」
  → user「じゃあこの窓口を出すわ」→ public/ に置く
```

逆に「たぶん要るだろうから公開しておく」は**この向きに反する**。

---

## 公開ホストサービス（Open Host Service, OHS）

**供給側が「誰でも使ってよい窓口」を用意する**パターン。
利用者が増えたとき、相手ごとに個別対応するのをやめて、共通の窓口を 1 つ開ける。

Customer/Supplier との違いは**相手の数**。1 対 1 なら Customer/Supplier、
1 対 多になったら OHS へ育てる、という理解でよい。

**この repo**: `<ctx>/public/` というディレクトリそのものが OHS の器。
いまは中身が 1 本（auth 向け）なので実質 Customer/Supplier だが、
**2 つ目のコンテキストが来ても同じ場所に置ける**形にしてある。

---

## 公表された言語（Published Language）

**コンテキスト間でやりとりするための、共有された語彙。**
OHS とセットで使われることが多い（窓口を開けるなら、そこで話す言葉も決めておく）。

**この repo**: `UserId`。auth の `RefreshToken` が `userId: UserId` を持ち、
`VerifyCredentialsQueryService` も `Option<UserId>` を返す。

値オブジェクトが越境してよいのはこのため。**変わる理由がない語彙**だから共有できる。

## 腐敗防止層（Anti-Corruption Layer, ACL）

**下流が上流のモデルを自分の言葉に翻訳する層。**
（上流 = 供給側、下流 = 使う側。[方向を間違えやすいので先頭の節を参照](#先に-上流下流はレイヤーの上下と方向が逆)）

> An Anti-corruption Layer is how a downstream context says "**no**" politely.
> — 上流の API を変換層で包み、上流のモデルを自分の概念と言葉に変換する
>
> 下流のコンテキストが、自分と上流の間に層を実装し、**上流から渡された
> オブジェクトを自分のモデルへ翻訳する責務**を持つ

**なぜ下流に置くのか。** 被害を受けるのが下流だから。上流が形を変えても
下流は自分のモデルを守れる、というのがこの層の目的。**川下の人が浄水器を置く**のと同じ。

使う場面は「**上流の形が気に入らないが、変えてもらえない**」とき。
レガシーシステムや外部 SaaS が典型で、そのモデルが自分のドメインに漏れてくるのを防ぐ。

**この repo には無い。** 理由は、上流（user）が下流（auth）の要求に合わせて
窓口を作ってくれるから。**Customer/Supplier が成立していれば ACL は要らない。**

|                       | 誰が形を決めるか                   | 変換層はどこ   |
| --------------------- | ---------------------------------- | -------------- |
| **Customer/Supplier** | 供給側が、使う側の要求に合わせる   | **要らない**   |
| **ACL**               | 上流が勝手に決める（変えられない） | **下流に置く** |

覚え方: **ACL は「相手が言うことを聞いてくれない」ときの防具。**
社内の別チームなら交渉できるので、まず Customer/Supplier を試す。

## 共有カーネル（Shared Kernel）

**複数のコンテキストが同じモデルを共有する。** 変更には全員の合意が要る。

**この repo**: `src/shared/domain/`。`MailAddress` / `Password` / `Uuid` など、
user も auth も同じ定義を使うもの。

便利だが**変更コストが高い**（片方の都合で変えられない）ので、置くものは絞る。

---

## 準拠者（Conformist）

**下流が上流のモデルにそのまま従う。** 翻訳も交渉もしない。
上流が強くて（外部 API など）、かつそのモデルで困らない場合の選択。

ACL との違いは「**防具を着るかどうか**」。着ないのが Conformist。

## god interface（神インターフェース）

**何でもできる巨大な窓口。** アンチパターン。

```ts
// これになったら黄信号
interface UserService {
  get / search / create / update / delete / verify / export / ...
}
```

何が問題か。

- **使う側ごとに必要なメソッドが違う**のに、全員が全部を握る
- 1 つ変えると**全利用者に波及**する
- 「誰がどれを使っているか」が追えなくなる

`public/` に「利用者を想定して先回りで作った汎用ポート」を置くと、これになりやすい。
だから **要求が出てから、要求の形で作る**。ポートが 5 本に増えても、
それは「5 つの頼み事がある」という事実がそのまま見えているだけで、悪いことではない。

## deep import / カプセル化違反

**モジュールの公開入口を通らずに、内部のファイルを直接 import すること。**

```ts
import { x } from "pkg"; // 入口を通っている
import { y } from "pkg/src/internal/y"; // deep import
```

TypeScript の境界強制ツール [Sheriff](https://github.com/softarc-consulting/sheriff) は
このルールを「Deep Import」から「**Encapsulation Violation**」に改名した。
問題の本体が「深さ」ではなく「**カプセル化を破ったこと**」だから。

**この repo**: `cross-context-public-only` が検出するのがまさにこれ。
`~/contexts/user/domain/user-repository` は deep import にあたる。

## モジュラーモノリス

**1 つのデプロイ単位の中を、独立したモジュールに分ける**構成。
マイクロサービスの「境界」だけを取り、分散システムの複雑さは買わない。

### 条件は 5 つ。ディレクトリを切るのはそのうち 1 つ

| 条件                                       | この repo での実体                                                   |
| ------------------------------------------ | -------------------------------------------------------------------- |
| ① **ドメインで縦に切る**                   | `contexts/user` / `contexts/auth`                                    |
| ② **各モジュールが自分のデータを所有する** | `tUser` は user、`tRefreshToken` は auth の `infrastructure/` にある |
| ③ **公開 API 経由でしかやりとりしない**    | `<ctx>/public/`。境界を跨ぐ外部キーは **0 本**                       |
| ④ **境界をツールで強制する**               | `dependency-cruiser` の `cross-context-public-only`                  |
| ⑤ **デプロイ単位は 1 つ**                  | `bun run src/main.ts`                                                |

**②〜④が本体。** ①だけなら _package by feature_ であって、モジュラーモノリスではない。

原則の出典はこう。

> 他のモジュールは内部実装に手を伸ばしてはならない — **公開インターフェースのみを呼べる**。
> 境界は規約ではなく**ツールで強制**しなければならない。
>
> データベースが共有でも、**各モジュールは自分のテーブルを所有する**。
> モジュール間のデータアクセスは**モジュールの API を経由**し、直接 SQL join はしない。

### 「切っただけ」との違い

同じディレクトリ構成でも、これをやった時点で成立しない。

```ts
// auth が user のテーブルを直接掴んで join する
import { tUser } from "~/contexts/user/infrastructure/drizzle-schema";
db.select().from(tRefreshToken).innerJoin(tUser, ...);
```

ディレクトリは分かれているのに **DB のレイヤーで癒着している**。user がテーブルを
変えた瞬間に auth が壊れるので、分けた意味が無い。

だからこの repo は境界を跨ぐ外部キーを 1 本も張っていない。参照整合性は DB 制約ではなく
**auth 側の手順**（user が消えたら券も片付ける）で保つ（[`../01-database.md`](../01-database.md)）。

### 隣の構成との位置関係

|                        | 切り方                                 | 壁                       | デプロイ     |
| ---------------------- | -------------------------------------- | ------------------------ | ------------ |
| **レイヤードモノリス** | 層で切る（`controllers/` `services/`） | 無い（全部が全部に届く） | 1 つ         |
| **モジュラーモノリス** | **ドメインで切る**                     | **機械で強制**           | **1 つ**     |
| **マイクロサービス**   | ドメインで切る                         | ネットワーク             | **バラバラ** |

ネットワーク越しの失敗も、結果整合も、分散トランザクションも買わない。
それでいて境界が守られているので、**後からマイクロサービスへ割れる**。
レイヤードモノリスから割るのはほぼ不可能（癒着しているため）。

> **この repo が④を満たしたのは 2026-08-12。** それまで境界ルールは blocklist で、
> `UserRepository` が他コンテキストから素通りしていた。「規約はあるが機械が守っていない」
> 状態は、この分類ではモジュラーモノリスに届いていない。

## 言語ごとの「公開面」の作り方

|                     | 仕組み                               | 強制するのは        | 向き                   |
| ------------------- | ------------------------------------ | ------------------- | ---------------------- |
| **Go**              | `internal/` ディレクトリ             | **コンパイラ**      | 置き忘れたら**公開**   |
| **Java 9+**         | `module-info.java` の `exports`      | コンパイラ + 実行時 | 置き忘れたら非公開     |
| **Spring Modulith** | `package-info.java` + 検証テスト     | **テスト**          | 置き忘れたら公開       |
| **npm / Node**      | `package.json` の `exports`          | **ランタイム**      | 置き忘れたら非公開     |
| **Nx / Sheriff**    | `index.ts`（バレル）を公開面にする   | lint                | 置き忘れたら非公開     |
| **この repo**       | `<ctx>/public/` + dependency-cruiser | lint                | **置き忘れたら非公開** |

Go の `internal/` が有名だが、**向きは逆にしてある**。
`internal/` 方式は「置き忘れたら公開」、`public/` 方式は「**置き忘れたら非公開**」。
新しいファイルを足したとき、うっかり境界が開くことがない。

TypeScript 界隈の主流は `index.ts` をバレルにする方式（Nx / Sheriff）だが、
この repo は[バレルを置かない](../02-architecture.md#バレルを置かない)方針なので採らなかった。
ディレクトリの位置で同じことを表現している。
