# 資格情報の照合をどこに置くか

**結論: ドメインサービス `verifyCredentials`（2026-08-11）。**
アダプタに書いていたものを、user の domain へ引き上げた。

---

## 何に迷ったか

`VerifyCredentialsQueryServiceLive`（user の infrastructure）に、照合の手順が
**丸ごと書かれていた**。リポジトリを引き、パスワードを照合し、`Option<UserId>` に畳む。

出た問いはこれ。

> `VerifyCredentialsQueryServiceLive`、これについて突っ込みます

---

## 最初の指摘は 3 分の 2 が誤りだった

当初「CQRS のクエリなのに」という理由を 3 つ挙げたが、**2 つは撤回した**。

| 挙げた理由                           | 判定                                 |
| ------------------------------------ | ------------------------------------ |
| クエリがリポジトリを使っている       | **誤り。** CQRS はそれを禁じていない |
| クエリが集約を復元している           | **誤り。** 同上                      |
| アダプタに業務ロジックが書かれている | **これだけが正しい**                 |

きっかけはこの問い。

> そもそもなんだけどさ、CQRS の query の流儀って、
> 他のドメインのリポジトリは触れないという流儀なんだっけ？

Microsoft の原文を読み直した。

> 集計などの DDD パターンからの制約を使用して**クエリを制限するのではなく、
> クエリの柔軟性を高める**

これは**許可**であって禁止ではない。「クエリは DDD パターンに縛られなくてよい」
と言っているだけで、「リポジトリを使うな」とは書いていない。

**規約を持ち出す前に一次情報を読む。** ここで学んだ。

---

## 残った 1 つが決め手

**アダプタに業務ロジックがある**こと。

`*Live` は「外の技術を自分のドメインへ翻訳する」層で、`SQL を書く` `HTTP を叩く`
`ライブラリを呼ぶ` が仕事。**「このメールアドレスとパスワードの組は誰か」は業務の問い**で、
技術の翻訳ではない。

そして [判断の順序](../README.md#判断の順序) に当てはめるとこうなる。

1. ビジネス側に聞ける問いか → **はい**（「ログインの条件は？」は仕様）
2. 集約 1 つを見て答えられるか → **いいえ**（まず引き当てが要る）
3. → **ドメインサービス**

`checkMailAddressDuplication` とまったく同じ形（引き当て → 判定）だったので、
置き場も揃えた。

---

## 引き上げた結果

`*Live` に残ったのは**語彙の変換と配線だけ**になった。

```text
public/verify-credentials-query-service.ts   ポート（auth に見せる面）
domain/services/verify-credentials.ts        照合そのもの ← ここへ移した
infrastructure/…-live.ts                     string → 値オブジェクト の変換と provideService
```

副産物として、**アダプタの doc が「SQL は書かない」と言い切れる**ようになった。

---

## なぜ「居ない」と「合わない」を区別しないか

どちらも `Option.none` に畳む。書き分けると、総当たりでメールアドレスの登録有無を
判定できてしまう（**アカウント列挙**）。401 へ翻訳するのは呼び出し側（auth）の責務。

この判断はドメインサービス側に置いてある。**列挙対策は業務の要求**であって、
アダプタの都合ではないため。
